## What This Repository Owns

- The **composed** per-audience specs in `published/` that the dev portal serves.
- The **composition policy** in `bin/compose` — how many service specs become one coherent public contract.
- The **canonical documentation overlays** in `canonical/` for models shared by several services.
- The composite's **version and immutable tag** (`v0.1.<height>`), which the portal pins.

It does **not** own the service specs themselves. Those are generated and pushed by each owning service.

## The Three Kinds of File — Read This First

The single most important thing to understand here: **almost nothing in this repo is hand-editable.**

| Path | Origin | Hand-edit? |
| --- | --- | --- |
| `specs/<service>-<audience>/openapi.json` | Generated by the owning service's build; pushed here by the shared [`publish-openapi-spec`](https://github.com/SymplastLLC/devops-actions/tree/main/.github/actions/publish-openapi-spec) action | **No.** Overwritten on the service's next push. Fix the service. |
| `published/<audience>-api.json` | Generated by `bin/compose` in CI and committed by the bot | **No.** Overwritten on the next compose. Fix `bin/compose` or a `canonical/` overlay. |
| `canonical/<audience>/<Name>.json` | Hand-authored, reviewed in PRs | **Yes** — this is the one content artifact you may edit |
| `bin/compose`, `.github/workflows/compose.yaml`, `README.md`, `AGENTS.md`, `version.json` | Hand-authored | **Yes** |

If a published model looks wrong, the fix is upstream in the owning service or in a `canonical/` overlay — **never** in `specs/**` or `published/**`.

## Audience Naming

A surface directory is `<service>-<audience>`; **the audience is the segment after the final `-`.**

```
specs/appointments-api-public/openapi.json   → audience: public
specs/financials-api-public/openapi.json     → audience: public   ├─► published/public-api.json
specs/legacy-api-public/openapi.json         → audience: public
specs/appointments-api-practice/openapi.json → audience: practice ──► published/practice-api.json
```

Audiences are **discovered** from the directory names, but an audience only publishes once it has a case in
`audience_meta()` in `bin/compose` supplying its title and server URL. An audience with specs but no case is
skipped with a warning — never published under a wrong title or host.

## Model Resolution (how names in the composite are decided)

This is the core policy of `bin/compose`. **Component and tag names are never prefixed** — the composite
reads as one unified API (`PublicCreditNote`, not `Symplast_Financials_Public_API_PublicCreditNote`).

Because names are unprefixed, a schema name defined by two or more specs *of the same audience* must resolve
to exactly one model. `bin/compose` resolves it before joining:

| Case | Behavior |
| --- | --- |
| Name appears in only one spec | Passes through unchanged |
| Same name, **same shape**, `canonical/<audience>/<Name>.json` exists | Unified into one component using the overlay's annotations |
| Same name, **same shape**, no overlay | Unified using the **first spec's** annotations, plus a `::warning::` telling you to add an overlay |
| Same name, **different shapes** | **Hard failure.** Nothing is published |
| Overlay's shape ≠ the specs' shape | **Hard failure.** Nothing is published |

"Same shape" is compared **annotation-insensitively** — `description`, `example`, `examples`, `title`,
`summary`, `externalDocs`, and `deprecated` are ignored, because independently generated specs routinely
disagree on prose while describing an identical structure.

The comparison is deliberately **schema-aware**, not a blanket `walk(del(.description))`. A blanket strip
would also delete a *property named* `description` — `PaymentTypeLookup` has one — silently making unequal
shapes compare equal. If you touch `JQ_CANON_DEF` in `bin/compose`, preserve that property.

### Why hard failure

Two different shapes under one name in a *published* contract is a contract bug. Masking it with a
per-service name prefix ships an incoherent public API. Failing the publish forces reconciliation upstream.

**Consequence to be aware of:** a downstream service's spec push can now turn this repo's `main` red. That is
intended. Do not "fix" it by reintroducing prefixing — reconcile the schema in the owning services, or rename
one of them.

## Canonical Overlays

When several specs of one audience define the same schema, the composite needs ONE set of docs for the
unified model. That is `canonical/<audience>/<SchemaName>.json`, containing the full schema definition.

Rules that matter:

- **Per-audience, never shared.** There is no global overlay directory and no fallback between audiences.
  `public` will not borrow `practice`'s overlay. Surfaces evolve independently; coupling their documentation
  would let a change to one silently alter another.
- **Annotations only.** The overlay's shape is verified against what the services actually emit; a mismatch
  fails the compose. An overlay can never become a place where the published contract drifts from the
  running APIs.
- Because of that guard, an overlay **cannot add a property**. If a field belongs in the contract, declare it
  in the owning services.
- Prefer neutral, service-agnostic wording. The overlay documents a model that now spans every operation in
  the audience, so a service-specific example is misleading.

To see the overlays that exist right now, list them rather than trusting this doc: `find canonical -type f`.

## Build, Test, and Run

| Task | Command |
| --- | --- |
| Compose everything locally | `COMPOSITE_VERSION=0.0.0-local bin/compose` |
| Inspect a composite | `jq '{info, pathCount: (.paths\|keys\|length), schemaCount: (.components.schemas\|keys\|length)}' published/public-api.json` |
| List composed model names | `jq -r '.components.schemas\|keys[]' published/public-api.json` |
| Check for unresolved refs | see the `$ref` one-liner in Troubleshooting below |
| Lint the workflow | `actionlint .github/workflows/compose.yaml` |
| Syntax-check the composer | `bash -n bin/compose` |
| Restore / Build / Test / Format | Not applicable — no application code |

`COMPOSITE_VERSION` is the composer's only input; any placeholder works locally. `bin/compose` is portable to
**bash 3.2** (macOS system bash) on purpose, so a local run behaves exactly like CI — do not introduce
associative arrays or other bash 4+ features.

**Local runs rewrite `published/`.** Revert it when you are done (`git checkout published/`) — the real
artifact is produced by CI with the real version.

## Versioning

The composite is this repo's own artifact, so its version is **this repo's** nbgv version — never a
downstream service's build number.

- `compose.yaml` resolves it via the shared [`calculate-version`](https://github.com/SymplastLLC/devops-actions/tree/main/.github/actions/calculate-version)
  action, the same action the other SymplastLLC repos use. The action emits **SemVer2** and supplies its own
  checkout; `nbgv` is already present on the runner, so nothing needs installing.
- `version.json` marks `main` as a public release ref, so on `main` SemVer2 is a clean `0.1.<height>`. A run
  from any other branch deliberately gets a `-g<commit>` suffix so it cannot masquerade as a release.
- The same value is stamped into every composite's `info.version` **and** used for the immutable git tag
  `v<version>`, so the version inside the spec always equals the tag consumers pin by.
- `version.json`'s `pathFilters` exclude `published/**`, so the bot's own compose commits do not inflate the
  height. Edits to `canonical/**` and `bin/compose` **do** count — they change the published contract.

## CI/CD

`.github/workflows/compose.yaml`, on push to `main` under `specs/**`, `canonical/**`, or `bin/compose`
(plus `workflow_dispatch`):

1. Checkout (full history — nbgv needs it).
2. Resolve version via the shared action.
3. `bin/compose` — fails the run on an unresolved schema conflict, publishing nothing.
4. Commit `published/` back to `main` as `github-actions[bot]`.
5. Tag the commit `v<version>` (idempotent; skipped when the tag exists).

The trigger excludes `published/**` so the bot's own commit does not retrigger the workflow.

## Agent Rules

- Read this file first.
- **Never hand-edit `specs/**` or `published/**`.** They are generated. See the three-kinds-of-file table.
- Prefer minimal, targeted changes.
- **Verify by running the composer** — `COMPOSITE_VERSION=0.0.0-local bin/compose` — before claiming a
  composition change works. There is no test suite to lean on. Then revert `published/`.
- When changing composition behavior, exercise the failure paths too, not just the happy path: divergent
  shapes and overlay drift must still hard-fail.
- Do not reintroduce component or tag name prefixing to work around a conflict. Reconcile upstream.
- Do not weaken a hard failure into a warning without explicit human approval — the hard failures are the
  contract guarantee, not defensive noise.
- Renaming a published component is a **breaking change** for consumers' generated clients. Flag it; the
  version tag lets the portal pin the old names.
- Shell scripts live in `bin/`, are executable, and carry no file extension.
- Markdown tables use spaces around the `|` separators to satisfy the linter.
- When you add, rename, or remove endpoints, services, audiences, overlays, or dependencies — update
  `AGENTS.md` and `README.md` in the same PR.

## Do Not Touch Without Explicit Approval

- `version.json` — `publicReleaseRefSpec` keeps published versions clean and `pathFilters` keeps the height
  meaningful. Changing either silently changes every future version and tag.
- The `git commit` / `git push` / tagging steps in `compose.yaml` — they write to `main` and create immutable
  tags the portal pins.
- The hard-failure branches in `bin/compose`.

## Troubleshooting

| Symptom | Cause / fix |
| --- | --- |
| `Schema 'X' has DIVERGENT shapes across the '<aud>' specs` | Two services define `X` differently. Reconcile in the owning services, or rename one. Not fixable here |
| `Canonical overlay '...' does not match the shape the '<aud>' specs emit` | The services changed shape, or the overlay tried to change it. Regenerate the overlay from a current spec, keeping only annotation edits |
| `Schema 'X' is shared by N specs ... but has no canonical/<aud>/X.json` | Working as designed. Add the overlay to control the unified model's docs |
| `Audience '<aud>' has specs but no audience_meta case` | Add a case to `audience_meta()` in `bin/compose` with the audience's title and server URL |
| `redocly join` exits non-zero after unification | A genuine collision survived unification (e.g. duplicate `operationId` or path). Inspect the redocly message; do not add prefixing |
| `bin/compose: line N: <name>: unbound variable` on macOS | A bash 4+ feature crept in. System bash is 3.2 — keep the script portable |
| Composite has a dangling `$ref` | `jq -r '[paths(objects) as $p\|getpath($p)\|select(type=="object" and has("$ref"))\|.["$ref"]]\|unique\|.[]' published/public-api.json` and compare against `jq -r '.components.schemas\|keys[]'` |

## Known Unknowns

- No `.github/CODEOWNERS`, so `ownerTeam` is unconfirmed.
- `code` appears in `ProblemDetails` examples in `appointments-api-public` and `legacy-api-public`, and
  `legacy` describes it as the discriminating extension member, but **no spec declares it as a property**.
  The canonical overlay omits it deliberately; declaring it is an upstream change in the owning services.
- Per-environment versioned promotion (`published/<env>/<audience>-api.json`) is deferred — see `README.md`.
- RFC-009 (Agent Documentation Structure) is still **Draft**. If it is accepted, this repo will additionally
  need `.agent/repo-context.json` and the five `docs/*` files.
